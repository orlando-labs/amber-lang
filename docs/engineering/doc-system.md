# Documentation system

Two generated documentation surfaces feed the website (`site/`):

1. **The Guide** — a bilingual, example-led *knowledge graph* of Markdown nodes
   that teaches the language step by step (`site/learn.html`).
2. **The module reference** — auto/best-effort API pages for the native VM
   modules, generated from the runtime source of truth plus curated examples
   (`site/modules.html`).

Both render client-side through the shared Markdown renderer in
`site/md-render.js` (no build step, no third-party deps).

---

## 1. The Guide (knowledge graph)

### Layout

```
site/guide/
  content/
    categories.yaml            # sidebar sections (id, order, bilingual titles)
    01-intro/overview.ru.md     # one file per node per language
    01-intro/overview.en.md
    02-language-core/blocks.ru.md
    ...
  guide-manifest.json          # GENERATED by tools/gen_guide_manifest.py
```

Each node is **one Markdown file per language**: `<id>.ru.md` and `<id>.en.md`.

### Node frontmatter

```yaml
---
id: blocks                      # stable node id (same across languages)
title: Блоки и block suffix      # localized (per file)
summary: Одна строка для карточек и графа.
category: language-core          # must exist in categories.yaml
order: 20                        # sort order within the whole graph
prerequisites: [overview]        # inbound graph edges (read these first)
related: [functions]             # outbound graph edges (go here next)
status: draft                    # draft | review | stable (badge in sidebar)
spec_refs:                       # ISOLATED — see §3 (removable later)
  - anchor: 5-блоки-лямбда-аргументы-и-placeholders
    label: Spec §5
---
```

### Body conventions

- Regular Markdown: headings, lists, tables, fenced code (```` ```amber ````).
- **Admonitions**: a blockquote whose first line is `[!note]`, `[!tip]`,
  `[!warn]` or `[!spec]` renders as a colored callout.
- **In-graph links**: `[text](guide:<node-id>)` navigates within the Guide.
- **Spec links**: `[§5](spec:<anchor>)` renders as a distinct chip pointing at
  `spec.html#<anchor>` (isolated coupling, see §3).
- **Examples must be real.** Every runnable snippet should end in a `# => <value>`
  line whose value is the actual output. Verify with:
  `printf '<program>' | ./build/amberc /dev/stdin` (or drop it into a temp file).

### Add a node

1. Create `site/guide/content/<NN-category>/<id>.ru.md` and `<id>.en.md`.
2. Fill the frontmatter; point `prerequisites`/`related` at existing node ids.
3. Regenerate and validate the graph:
   ```
   python3 tools/gen_guide_manifest.py            # writes guide-manifest.json
   python3 tools/gen_guide_manifest.py --check     # CI gate: non-zero on a broken graph
   ```
   `--check` fails on unknown categories, dangling prereq/related links, or
   malformed frontmatter; it warns on a missing translation.

## 2. The module reference (generator)

### Sources, by trust

1. **Registry selectors** — `selector == "..."` literals in
   `runtime/stdlib_*.cpp` are the authoritative method surface. The generator
   diffs them against the documented methods (the **drift guard**).
2. **Sidecars** — `docs/module-examples/<id>.sidecar`, human-authored module
   metadata + per-method blurbs and examples.
3. **Corpus** — `corpus/run/<dir>` programs are verified by construction; a
   `corpus:` method inlines that program and its `expect.run.json` value.

### Sidecar format

Header keys, then one block per method. Example blocks are captured **verbatim**
between `example:` and a `.end` sentinel (no dedent), so code with `:` and quotes
is lossless.

```
id: base64
path: base64.html
title: Base64
icon: 64
source: runtime/stdlib_codecs.cpp        # translation unit for the drift guard
description.ru: ...
description.en: ...
note.ru: ...
note.en: ...
drift_ignore: [selectorA, selectorB]     # known-undocumented selectors (TODO), surfaced as `pending`

method: Base64.encode(bytes, padding: true)
ru: Кодирует байты стандартным alphabet.
en: Encodes bytes with the standard alphabet.
example:
text = Base64.encode(Bytes.new("hello"))
# => "aGVsbG8="
.end

method: Worked example — parse, match, round-trip
corpus: json_parse_generate              # instead of `example:` — inlines the verified program
ru: ...
en: ...
```

- A method's **selector** is inferred from its signature (`Base64.encode(...)` →
  `encode`, `time.year` → `year`); operator signatures (`time + period`) have no
  selector. Override with an explicit `selector: <name>` line when needed.
- `drift_ignore` is the escape hatch for selectors that exist in the runtime but
  are not yet documented (e.g. a freshly-landed API). They are **not hidden** —
  the coverage report lists them under `pending`.

### Run it

```
python3 tools/gen_module_docs.py            # writes site/modules-data.js + site/modules-coverage.json
python3 tools/gen_module_docs.py --verify    # additionally runs inline `# =>` examples through build/amberc
python3 tools/gen_module_docs.py --check      # drift guard only; non-zero when the runtime exposes an undocumented, non-ignored selector
```

`--verify` is best-effort: only examples with a `# => <output>` line are checked;
anything needing capabilities, I/O, randomness or time stays `unverified` and
never fails the run. Verified counts and gaps land in
`site/modules-coverage.json`.

Corpus-backed examples are verified by construction (the corpus suite runs in
CI), so they are not re-executed here.

### Re-seed the sidecars

The sidecars were bootstrapped once from the previous hand-written
`site/modules-data.js` with `tools/seed_module_sidecars.py`
(`node`-dump → sidecars). That script is kept for provenance; day-to-day you edit
the sidecars directly and regenerate.

## 3. Removing the spec references later

The Guide is meant to become a **self-contained** language document. All coupling
to the formal `amber_unified_final_spec.md` is deliberately confined to two
grep-removable conventions:

1. The `spec_refs:` frontmatter key on Guide nodes.
2. Inline `spec:` scheme links (`[label](spec:anchor)`).

To turn spec references off site-wide **without deleting anything**, set
`show_spec_refs` to `false` in `tools/gen_guide_manifest.py` (the manifest flag
the renderer honors) and regenerate.

To remove them permanently:

```
# 1. drop the spec_refs blocks from every node
grep -rl 'spec_refs:' site/guide/content
# 2. find inline spec links to rewrite as in-graph links or prose
grep -rn '(spec:' site/guide/content
```

Then regenerate the manifest. Nothing else in the Guide, the renderer, or the
module reference depends on the spec.
